ঠিক বলেছেন। আগেরটা আমি **overview** হিসেবে বেশি short করে ফেলেছিলাম। আপনি যেহেতু **production-grade NestJS backend** শিখছেন, এখন থেকে প্রতিটি topic আমি **concept → কেন দরকার → code → request/response → production practice → common mistake** এইভাবে বিস্তারিত শেখাব।

# 1. REST API Design

## REST API কী?

REST হলো API design করার একটা standard approach।

সহজভাবে:

> **URL দিয়ে resource বোঝাবেন এবং HTTP method দিয়ে operation বোঝাবেন।**

ধরুন আমাদের resource হলো `users`।

তাহলে:

```http
GET    /api/v1/users
GET    /api/v1/users/123
POST   /api/v1/users
PATCH  /api/v1/users/123
DELETE /api/v1/users/123
```

এগুলো ভালো REST design।

---

## কেন এমন?

ধরুন:

```http
GET /users
```

মানে:

> আমাকে users দাও।

আর:

```http
POST /users
```

মানে:

> নতুন user তৈরি করো।

একই URL:

```text
/users
```

কিন্তু HTTP method আলাদা হওয়ায় operation আলাদা।

---

## ❌ খারাপ API design

অনেক beginner এমন করে:

```http
GET  /getUsers
POST /createUser
POST /deleteUser
POST /updateUser
```

এখানে HTTP method-এর power ব্যবহার করা হচ্ছে না।

---

## ✅ Better

```http
GET    /users
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

---

## NestJS code

```ts
@Controller('users')
export class UsersController {
  @Get()
  findAll() {
    return 'Get users';
  }

  @Get(':id')
  findOne(@Param('id') id: string) {
    return `Get user ${id}`;
  }

  @Post()
  create() {
    return 'Create user';
  }

  @Patch(':id')
  update(@Param('id') id: string) {
    return `Update user ${id}`;
  }

  @Delete(':id')
  remove(@Param('id') id: string) {
    return `Delete user ${id}`;
  }
}
```

এখন API:

```text
GET    /users
GET    /users/123
POST   /users
PATCH  /users/123
DELETE /users/123
```

# 2. DTO

DTO = **Data Transfer Object**

DTO-এর কাজ:

> Client কী ধরনের data পাঠাবে তার একটা contract তৈরি করা।

ধরুন registration API:

```http
POST /api/v1/auth/register
```

Client পাঠাবে:

```json
{
  "name": "Rahim",
  "email": "rahim@gmail.com",
  "password": "secret123"
}
```

এখন DTO:

```ts
export class RegisterDto {
  name: string;
  email: string;
  password: string;
}
```

কিন্তু এখানে সমস্যা আছে।

এই DTO বলছে shape কী হবে, কিন্তু:

```text
email valid কিনা?
password কত বড়?
name string কিনা?
```

এসব check করছে না।

সেজন্য `class-validator` লাগবে।

---

# 3. class-validator

Install:

```bash
npm install class-validator class-transformer
```

DTO:

```ts
import {
  IsEmail,
  IsString,
  MinLength,
  MaxLength,
} from 'class-validator';

export class RegisterDto {
  @IsString()
  @MinLength(2)
  @MaxLength(50)
  name: string;

  @IsEmail()
  email: string;

  @IsString()
  @MinLength(8)
  @MaxLength(100)
  password: string;
}
```

এখন validation rules:

```text
name
 ├── must be string
 ├── minimum 2 characters
 └── maximum 50 characters

email
 └── valid email হতে হবে

password
 ├── string
 ├── minimum 8
 └── maximum 100
```

---

# 4. Request Validation

এখন DTO বানালেই হবে না।

NestJS-কে বলতে হবে:

> "Request আসলে DTO-এর validation চালাও।"

`main.ts`:

```ts
import { ValidationPipe } from '@nestjs/common';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  await app.listen(3000);
}

bootstrap();
```

এখন একটু বুঝি।

---

## `whitelist`

ধরুন client পাঠাল:

```json
{
  "name": "Rahim",
  "email": "rahim@gmail.com",
  "password": "secret123",
  "isAdmin": true
}
```

কিন্তু DTO:

```ts
export class RegisterDto {
  name: string;
  email: string;
  password: string;
}
```

`isAdmin` DTO-তে নেই।

`whitelist: true` হলে extra property remove করার behavior পাওয়া যায়।

---

# `forbidNonWhitelisted`

আমি production API-তে সাধারণত এটাও ব্যবহার করতে পছন্দ করব।

তখন extra property পাঠালে request reject হবে।

```json
{
  "name": "Rahim",
  "email": "rahim@gmail.com",
  "password": "secret123",
  "isAdmin": true
}
```

Response:

```http
400 Bad Request
```

কারণ:

```text
isAdmin
   ↓
DTO-তে নেই
   ↓
❌ Request rejected
```

এটা security এবং API contract দুটো দিক থেকেই useful।

---

# `transform`

Query parameter এবং route parameter সাধারণত string হিসেবে আসে।

ধরুন:

```http
GET /users?page=2
```

HTTP request থেকে:

```ts
page = "2"
```

আসে।

কিন্তু আমরা চাই:

```ts
page = 2
```

এজন্য `transform: true` ব্যবহার করা যায়।

DTO:

```ts
import { Type } from 'class-transformer';
import { IsInt, Min } from 'class-validator';

export class UserQueryDto {
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page = 1;
}
```

এখন:

```text
"2"
 ↓
Number transformation
 ↓
2
```

# 7. class-transformer

`class-transformer` মূলত object transformation এবং serialization-এ অনেক কাজে আসে।

ধরুন database থেকে user পেলাম:

```ts

  name: 'Rahim',
  email: 'rahim@gmail.com',

  refreshToken: '....'

```

কিন্তু client-কে এগুলো পাঠানো যাবে না।

আমরা চাই:

```json
{
  "id": "123",
  "name": "Rahim",
  "email": "rahim@gmail.com"
}
```

এখানে response serialization গুরুত্বপূর্ণ।

# 8. Response DTO

একটা response DTO তৈরি করি:

```ts
import { Exclude, Expose } from 'class-transformer';

export class UserResponseDto {
  @Expose()
  id: string;

  @Expose()
  name: string;

  @Expose()
  email: string;

  @Exclude()
  password: string;

  @Exclude()
  refreshToken: string;
}
```

এখন sensitive data explicitly exclude করা যায়।

# 11. Pagination

ধরুন database-এ:

```text
1,000,000 users
```

আপনি যদি করেন:

```http
GET /users
```

এবং এক million user ফেরত দেন—

💥 Bad idea.

Database → Backend → Network → Browser

সব জায়গায় চাপ পড়বে।

তাই pagination।

```http
GET /users?page=1&limit=20
```

মানে:

```text
page = 1
limit = 20
```

---

# Pagination DTO

```ts
export class PaginationDto {
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page = 1;

  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)
  limit = 20;
}
```

আমি এখানে `Max(100)` দিয়েছি কারণ client যেন এমন না পাঠায়:

```http
?limit=1000000
```

---

# Pagination calculation

ধরুন:

```text
page = 3
limit = 20
```

তাহলে database-এ সাধারণ ধারণা:

```text
skip = (page - 1) * limit

skip = (3 - 1) * 20
     = 40
```

তাই:

```text
page 1 → records 1-20
page 2 → records 21-40
page 3 → records 41-60
```

---

# Pagination Response

```json
{
  "success": true,
  "message": "Users fetched successfully",
  "data": [],
  "meta": {
    "page": 3,
    "limit": 20,
    "total": 150,
    "totalPages": 8
  }
}
```

Frontend এখন জানে:

```text
বর্তমান page = 3
প্রতি page = 20
মোট = 150
মোট page = 8
```

# 12. Filtering

Filtering মানে:


মানে:

```text

শুধু fruit
```

আর:

```http

```

মানে:

```text

```

# Multiple filters

```http

```

মানে:

```text
category = fruit

```

# Filter DTO

```ts
export class ProductQueryDto {
  @IsOptional()

```

এখানে:

```ts
@IsOptional()
```

মানে field না দিলেও সমস্যা নেই।

# 13. Sorting

ধরুন products price অনুযায়ী sort করতে চাই:

```http
GET /products?sortBy=price&sortOrder=asc
```

মানে:

```text
price
10
20
30
40
```

Descending:

```http
GET /products?sortBy=price&sortOrder=desc
```

```text
40
30
20
10
```

---

# Sort DTO

```ts
export class ProductQueryDto {
  @IsOptional()
  @IsIn(['name', 'price', 'createdAt'])
  sortBy?: string;

  @IsOptional()
  @IsIn(['asc', 'desc'])
  sortOrder?: 'asc' | 'desc';
}
```

এখানে `@IsIn()` খুব গুরুত্বপূর্ণ।

Client যেন arbitrary field পাঠাতে না পারে।

---

# ❌ Dangerous approach

```ts
const sortBy = query.sortBy;

database.sort({
  [sortBy]: 1,
});
```

যদি allowed fields validate না করেন, তাহলে client আপনার database query behavior-এর ওপর অপ্রয়োজনীয় control পেতে পারে।

# 15. সব Query একসাথে

Production API-তে সাধারণত এগুলো একসাথে থাকবে।

```http
GET /products?page=2&limit=20&search=apple&category=fruit&sortBy=price&sortOrder=asc
```

DTO:

```ts
export class ProductQueryDto {
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page = 1;

  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)
  limit = 20;

  @IsOptional()
  @IsString()
  @MaxLength(100)
  search?: string;

  @IsOptional()
  @IsString()
  category?: string;

  @IsOptional()
  @IsIn(['name', 'price', 'createdAt'])
  sortBy?: string;

  @IsOptional()
  @IsIn(['asc', 'desc'])
  sortOrder?: 'asc' | 'desc';
}
```

Controller:

```ts
@Get()
findAll(@Query() query: ProductQueryDto) {
  return this.productService.findAll(query);
}
```

এখন controller-এর কাজ শুধু request নেওয়া।

Business logic যাবে service-এ।

```text
old clients
```

এজন্য versioning।

# 17. HTTP Status Codes

এগুলো মুখস্থ না করে situation অনুযায়ী বুঝুন।

---

## `200 OK`

সফল request।

```http
GET /users/123
```

Response:

```http
200 OK
```

---

## `201 Created`

নতুন resource তৈরি হয়েছে।

```http
POST /users
```

Response:

```http
201 Created
```

---

## `204 No Content`

Operation সফল কিন্তু response body নেই।

```http
DELETE /users/123
```

Response:

```http
204 No Content
```

---

# Client Error

## `400 Bad Request`

Request invalid।

যেমন validation failure:

```json
{
  "email": "hello",
  "password": "123"
}
```

---

## `401 Unauthorized`

User properly authenticated নয়।

যেমন:

```text
No access token
Invalid token
Expired token
```

---

## `403 Forbidden`

User কে চেনা গেছে, কিন্তু permission নেই।

```text
User
 ↓
Admin endpoint
 ↓
❌ 403
```

---

## `404 Not Found`

Resource নেই।

```http
GET /users/999
```

যদি user না থাকে:

```http
404 Not Found
```

---

## `409 Conflict`

Existing data-এর সাথে conflict।

যেমন:

```text
Email already exists
```

Response:

```http
409 Conflict
```

## `422 Unprocessable Entity`

# 🏆 আপনার জন্য API Design-এর Final Mental Model

এই flow-টা ভালোভাবে মাথায় বসান:

```text
                  API DESIGN
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
     REST            DTO          Status Codes
       │              │              │
       ↓              ↓              ↓
   Endpoints      Validation       200/201
                  │               400/401
                  ↓               403/404
          class-validator         409/500
                  │
                  ↓
          class-transformer
                  │
          ┌───────┴────────┐
          ↓                ↓
       Request          Response
       Transform        Serialize
          │                │
          └───────┬────────┘
                  ↓
          Pagination
          Filtering
          Sorting
          Searching
                  ↓
           API Versioning
                  ↓
       Consistent Response
                  │
          ┌───────┴────────┐
          ↓                ↓
       Success            Error
          ↓                ↓
       data/meta      message/errors
```

### সবচেয়ে গুরুত্বপূর্ণ ৫টা জিনিস আগে শক্ত করুন

আপনি production NestJS শিখছেন বলে আমি এই order-এ practice করতে বলব:

**1. REST API design**
→ resource, HTTP methods, URL structure

**2. DTO + class-validator**
→ API input-এর contract এবং validation

**3. ValidationPipe + class-transformer**
→ request clean/validate/transform

**4. Pagination + filtering + sorting + searching**
→ real-world list API

**5. Consistent response + error handling**
→ পুরো backend-এর predictable API contract

এরপর **API versioning + serialization + exception filters** করলে পুরো API Design section অনেক solid হয়ে যাবে।
