Copy env templates and fill in real values:

```bash
cp mobile/.env.example mobile/.env
cp backend/.env.example backend/.env
```

Then run each app in its own terminal:

```bash
pnpm backend:dev     # http://localhost:4000/health
pnpm mobile          # opens Expo Dev Tools
```

### One important extra step

Native module versions (react-native-svg, react-native-screens, netinfo, etc.)
were pinned to the latest versions compatible with SDK 56 at the time of
writing, but Expo's own compatibility table is the source of truth. After
`pnpm install`, run:

```bash
cd mobile && npx expo install --check
```

This will flag (and offer to fix) anything that's since drifted from what
SDK 56 expects — always trust `expo install` over hand-picked versions.

### Assets not included

`mobile/app.json` references `./assets/icon.png`, `splash.png`,
`adaptive-icon.png`, `favicon.png`, `notification-icon.png` — these are
binary files and weren't generated. `expo start` in Expo Go works without
them; a standalone/EAS build will fail until they're added.

## Architecture decisions made in this milestone

1. **pnpm workspaces monorepo** — one repo, two packages (`mobile`,
   `backend`), sharing a root `tsconfig.base.json` and Prettier config so
   both apps enforce the same strictness and formatting.

2. **Feature-based structure on both sides** — `mobile/src/features/*` and
   `backend/src/modules/*` mirror each other (see the README in each
   folder). A feature/module owns its UI or routes, business logic, and
   data access; nothing reaches across boundaries except through an
   explicit public entry point.

3. **No path aliases in the backend.** `tsx` (used for `pnpm backend:dev`)
   doesn't resolve `tsconfig.json` `paths` at runtime without extra tooling
   (`tsc-alias` at build time, or a custom loader). Rather than add that
   complexity now, backend imports are relative. The mobile app _does_ use
   `@/*` aliases — Metro resolves those natively via Expo's tooling, so
   there's no such tradeoff there.

4. **Supabase auth verification uses JWKS (asymmetric keys), not the
   legacy shared HS256 secret.** This is Supabase's current recommendation:
   the backend fetches and caches public keys from
   `/auth/v1/.well-known/jwks.json` and verifies tokens locally — no round
   trip to Supabase per request. If your Supabase project is still on the
   legacy symmetric secret, either migrate it (Dashboard → Project Settings
   → JWT) or extend `backend/src/middleware/auth.ts` to fall back to
   `SUPABASE_LEGACY_JWT_SECRET`.

5. **Supabase session storage uses a "LargeSecureStore" pattern**, not
   Secure Store directly. Supabase sessions routinely exceed Secure Store's
   ~2048-byte per-value limit, so a small AES-256 key lives in Secure Store
   (hardware-backed) and encrypts the actual session blob, which is then
   written to AsyncStorage. This is Supabase's own documented pattern for
   Expo apps — not a shortcut.

6. **Express 5's native async error handling** means no
   `express-async-errors` package is needed — thrown errors inside `async`
   route handlers are caught automatically and forwarded to
   `errorHandler.ts`.

7. **Structured logging with pino**, not `morgan` + `console.log`. JSON logs
   in production (searchable/parseable), pretty-printed in dev. `pino-http`
   auto-logs every request with timing.

## What's intentionally _not_ built yet

No feature modules (categories, lessons, vocabulary, quiz, ...), no
database schemas, no SQLite offline layer, no actual UI beyond a boot-check
screen. This milestone is tooling and scaffolding only, per the project's
"build one feature at a time" rule.

## Suggested next milestone

**Database schemas + the Categories module**, end to end: Mongoose schema →
repository → service → controller → route on the backend, matched by the
`categories` feature (SQLite table, React Query hooks, list screen) on
mobile. This is the smallest vertical slice that exercises the whole
architecture — auth, offline SQLite, sync, and the module convention — so
it's the right thing to get right before building the rest on top of it.
